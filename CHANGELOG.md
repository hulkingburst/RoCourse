# Changelog

## 2026-10-28

- Performance: the database work behind the site's small numbers now matches how small they are, after Neon began refusing every connection with `53000 Your account or project has exceeded the quota`. The data was never the problem — the leaderboard is names and XP, the landing counters are three integers — but the number of queries per view was. Five hot paths were cut: (1) `getSiteStats` runs a `jsonb_each` over every stored progress blob, and the home page is `force-dynamic`, so that scan ran once per request, crawlers included; it is now wrapped in `unstable_cache` for ten minutes (`src/lib/site-stats.ts`), with the zero fallback kept outside the cache so a failed read is not stored and a restored database is picked up on the next request. (2) The public leaderboard's `findMany` is cached for sixty seconds per week (`src/app/api/leaderboard/route.ts`); the caller's own-row `you` marker is applied after the cached read, so personalization is unchanged, and the friends view — which depends on who is asking — stays uncached. (3) `GET /api/polls` runs on every page load for every visitor and used to do two housekeeping database calls each time, including a `deleteMany` that retires closed polls' bell entries (a write even when it deletes nothing); both are idempotent and now run at most once per five minutes per instance. (4) A progress push no longer re-reads the whole cloud state after saving — five queries whose result every caller discarded — skips the cloud watermark entirely on a forced push, and reads the user's existing weekly rows in one `findMany` instead of one `findUnique` per week. (5) A guest's weekly-XP reporter debounced at two seconds, which is shorter than the gap between two lesson steps, so an active guest posted a row plus a rate-limit read and insert for nearly every step; the window is now eight seconds (`src/lib/use-guest-xp-reporter.ts`). The weekly board is a tally, not a live feed, and nothing is lost if the tab closes inside the window because the reporter posts the current total on the next load. Verified with `npx tsc --noEmit --incremental false`, `npx eslint` on the changed files and `npm run build`, all clean, and the home page still returns 200 from a dev server while the real database is refusing connections. The query-count reductions are by construction, not measured: the only database available is the one over quota, which rejects `SELECT 1` at connect time, so a before/after count has to wait until the project is reachable again.

- Temporary: the two places the quota is actually visible now say they are disabled instead of showing a blank or a lie. On the home page the three counters rendered `0` when the aggregate could not be read — a plausible number that was not true — so `getSiteStats` now reports `unavailable` and the cards show a dash with one small muted "Stats temporarily disabled" badge under the grid. On `/leaderboard` the same failure used to surface as the generic "Couldn't load the leaderboard" with a Retry button that could never work, so the route answers `503 { unavailable: true }` when a read fails and the client renders a small "Temporarily disabled" badge with one line explaining that the site has hit its usage limit for now. The detection is deliberately not a string match on Neon's `53000 … exceeded the quota` message: any failed read on these paths (quota, refused connection, outage) means the same thing to a learner, and both drivers' error shapes differ. A failed session read is also no longer mistaken for a signed-out visitor on the friends view. Strings in EN and ES. This is a label only — nothing is cached, retried or scheduled differently, and no notification was added. Verified against a real `next dev` while the database is still refusing connections: `/` returns 200 with three em dashes and the badge, and `/api/leaderboard` returns 503 with `unavailable: true`; `npx tsc --noEmit`, `npx eslint` on the changed files and `npm run build` are clean.

## 2026-10-13

- Security: the weekly board no longer hands every guest's id to every visitor. `GET /api/leaderboard` returned a `guestId` for each guest row, and the only consumer was the client's own `isMe` comparison — so the payload published a stable pseudonymous identity for every guest on the board. Rows now carry a server-decided `you` marker instead and no id at all: the server knows the caller's session for an account and, for a guest, verifies the signed token the caller presents for the id it names (`?guestId=…` plus an `x-guest-token` header, deliberately a header so the credential never lands in a URL). The marker reproduces the old predicate exactly — handle equality for accounts, and a guest is never marked while a session is present — so the rendering is unchanged; the only visible difference is that a device whose token has aged out refreshes it once and re-asks, which is why the endpoint reports `guestTokenStale` rather than silently dropping the learner's own badge. Verified end to end against the real database: with an account and with a proven guest id, the marked row is exactly the row the caller owns and never the top row, the payload contains no `guestId` key anywhere, and both viewers' markers match the previous client-side predicate row for row.

- Security: a guest identity is now only kept for the device that created it. `GET /api/guest-xp` re-signed any well-formed id a caller presented, so anyone who learned a live guest id — which the board itself was publishing until the change above — could be issued a valid token for it and then post as that learner, renaming or inflating their row. Issuance now demands proof only where there is something to take: an id nobody has posted for is still adopted as-is with no token, which keeps a first-time guest and a device with cleared storage exactly as free as they were, while an id that already has board rows is re-signed only for a caller holding a token this server issued for it. An *expired* token counts as proof, because the HMAC is what proves prior issuance and the key never leaves the server — so a returning device that comes back after its token ages out keeps its id and its row, and only a caller that merely names someone else's id is handed a fresh server-generated identity instead. Verified against the real route: fresh id adopted with no proof, unclaimed-but-presented id signed, claimed id refused without proof (returned a new uuid, row untouched), claimed id kept with a live token, with an expired token, and refused with a token issued for a different id or a forged signature.

- Fix: a stale device can no longer wipe a learner off the weekly board. `saveWeeklyXpRows` deleted every `WeeklyXp` row for a user whose blob arrived with an empty `weeklyXp`, and its own comment described that as the reset path — but a local blob that still has lessons and an empty weekly bucket is a client whose totals were lost, not a learner tidying up, and deleting on its word erased rows another device had earned. The empty branch now checks the snapshot for lesson records: with lessons present the rows are left untouched (the progress itself still stores), and with no lessons at all — what `resetProgress` produces, since it clears the map — the rows are pruned exactly as before. Verified against the real `saveCloudState`: a blob with lessons and an empty bucket stores and leaves the row at 4000 XP, a real claim below the stored total does not lower it, a higher one raises it, and a genuine reset still empties the rows.

- Hardening: state-changing requests now have to come from this site. Every `POST`/`DELETE` route under `src/app/api` (sync, guest-xp, polls, questions, answers, solved, follow, feedback, resource and showcase submissions, upload, verify, daily challenge, narration, notifications) runs `isSameOriginRequest` before it touches its input, which rejects a cross-site `Origin` and a `Sec-Fetch-Site: cross-site` request with 403 and leaves a caller with no `Origin` at all to the session check — page script always sets one for a non-GET, and a non-browser caller carries no cookies to abuse. The check accepts the host the request arrived on as well as the deployment's configured origins (`NEXT_PUBLIC_SITE_URL`, `AUTH_URL`/`NEXTAUTH_URL`, Vercel's deployment hosts, an `ALLOWED_ORIGINS` list): behind Vercel or Cloudflare that host is the public one the browser actually reached, whereas a configured-only list would fail closed on any deployment whose URL is not in the environment — the Workers build, a preview URL — which could not be verified from here. Verified over HTTP: a cross-site origin and a cross-site `sec-fetch-site` both 403, a same-origin mutation still reaches its handler and fails on its own merits (401 for a bad guest token), and a request with no `Origin` is not blocked.

- Hardening: personalized JSON can no longer be cached by anything. `Cache-Control: private, max-age=0, no-store` plus `Vary: Cookie` now go out from `/api/sync`, `/api/leaderboard`, `/api/notifications`, `/api/polls`, `/api/follow` and guest-identity issuance, from one shared constant, so a progress blob, a board with the caller's own row marked, a notification bell, or a guest token cannot be stored by a browser cache, a CDN, or a proxy shared with other visitors. Verified by reading the headers off live responses for all six routes.

- Hardening: the two missing indexes for the queries this round added or leaned on. The new "does this guest id already have rows" lookup is a filter on `guestId` alone, which the `(week, guestId)` unique index cannot serve because its leading column is the week, so it gets `WeeklyXp_guestId_idx`; completion lists are read per user in date order (the certificate page, the public profile), which the `(userId, courseId)` unique index can filter but not sort, so `CourseCompletion` gets `(userId, completedAt)`. Both are in the schema and in a new migration, which the Vercel build applies with `prisma migrate deploy`. Verified by running the migration's own DDL inside a transaction on the real database, confirming it applies cleanly, and rolling back — the check left no index behind. The planner still chooses a sequential scan at the current sizes (161 `WeeklyXp` rows, 1 `CourseCompletion` row), so no speedup is claimed at this volume; the index is insurance for the shape of the query, not a measured win.

- Hardening: removed dead code and stopped tracking local scratch. Nine exported symbols referenced nowhere in the repository are gone (`isActivityType`, `narrationVoiceFallbackId`, `getProfileViewer` and its `ProfileViewer` type, `isPollVotable`, `moderateGuestName`, `FINISHED_PATHS`, `localIsNewer`, `looksLikeZip`), along with `src/components/lessons/lesson-actions.tsx`, a component no route or lesson imported; exports that are only used inside their own module were left alone, since their bodies run and removing the keyword would be bookkeeping rather than a fix. The third-party list was written before PurgoMalum (profanity filtering on submitted public text), ElevenLabs (narration), DiceBear (profile pictures), and Cloudflare's hosting, Web Analytics and R2 existed, and the analytics section only described Vercel; both now say what is sent and to whom, including that password, email, and progress are never sent to any of them, and Cloudflare's cookieless-analytics claim is labelled as Cloudflare's. ## 2026-10-11

- Security: completion records are derived server-side from the progress blob, so a certificate can no longer be minted by a request. `POST /api/sync` used to persist the client's `completions[]` array verbatim, which meant any free account could create a `CourseCompletion` with an arbitrary course, title, and date — a shareable "RoCourse Certificate of Completion", a showcase submission, and the top of the weekly board from one authenticated POST. `saveCloudState` now ignores that field entirely and derives records from the sanitized blob instead, via one shared implementation (`src/lib/completions.ts`) that the client sync engine and the progress export also use, so there is no second derivation to drift from the server's. The derived date is clamped to a real past timestamp (a claimed future date stores as now), and rows whose evidence has disappeared — the learner un-completed the capstone — are deleted, which is what keeps the showcase gate and the weekly board resting on the same truth. This also resolves the "certificate dates are write-once" note: dates are re-derived on every sync rather than frozen from the first client that claimed one. Verified with a stubbed database against the real `saveCloudState`: a forged `completions[]` with no capstone evidence writes zero rows, capstone evidence writes exactly one record with the course and title derived from the chosen path, a forged 2027 date stores as today, and the update path carries the same derived date every time.

- Security: the resource upload bucket no longer deletes anything on a caller's word. `POST /api/resources/verify` took a URL, sniffed it, and called `deleteR2Object(url)` when the sniff said "not a zip" — and because the sniff failed closed, an unreachable URL or a failed fetch *was* the "not a zip" answer, so an anonymous caller could delete any object on an allowlisted host by naming it. Verification is now bound to proof of upload: `issueR2Upload` returns a signed, expiring token (HMAC over the object key, keyed by the deployment's own R2 secret) that the client echoes back, the URL must sit on this deployment's R2 public host, and the delete target is the token's key rather than the URL. The sniff is three-way (`zip` / `not-zip` / `unreadable`), and only a positive "these bytes are not a ZIP" finding deletes anything — a refused upload whose object could not be read is rejected and left alone for the sweep. Verified with a local server and the real module: valid, tampered, expired, wrong-object, claimed-key, and arbitrary-key tokens all behave (only the valid one authorizes), an unreachable host, a broken connection, and a 404 all read as `unreadable`, and only real non-ZIP bytes read as `not-zip`. The same three-way rule now also guards the Vercel Blob branch of the upload route, where a fetch failure previously deleted the blob it could not read.

- Security: multi-write operations are genuinely all-or-nothing instead of sequentially applied. The Workers SQL shim's `$transaction` was a `for` loop over already-issued statements — its callers (`changeUsername`'s user row plus denormalized leaderboard names, and the feedback ticket plus its notification) would half-apply on a mid-sequence failure, and the method is now gone rather than misleading, because the HTTP driver has no session to put `BEGIN`/`COMMIT` around. Both writes became single data-modifying CTE statements in `src/lib/db/atomic-writes.ts` (`renameUserWithLeaderboardName`, `recordFeedbackTicket`), which Postgres executes in one implicit transaction and which run unchanged on both the Prisma and the shim drivers. Verified against a real Postgres (PGlite): the rename reports and applies the user row plus both owned leaderboard rows while leaving the guest row alone, an unknown user changes nothing, the feedback statement writes both rows, stays idempotent on a repeat, and keeps an existing ticket's row — and when the second leg is forced to fail (a `Notification.title` that violates `NOT NULL`) the statement throws and no partial ticket survives.

- Fix: signing in on a second device no longer erases weekly leaderboard history. `saveWeeklyXpRows` pruned every row older than the oldest week in the incoming payload, so a fresh device (or a cleared browser) pushing a blob that only knew the current week deleted the weeks another device had earned — while the function's own comment promised rows were only ever raised. Incoming weeks are now unioned with what is stored, and the table is bounded by the retention window alone (26 weeks), never by the shape of the latest payload. The empty-blob branch still clears rows, which is what bounds the table when progress is reset. Verified against the real `saveCloudState` with a stubbed database: the prune predicate is the retention cutoff and never the payload's oldest week.

- Security: lesson narration now costs money only for signed-in learners. `POST /api/tts` called ElevenLabs on any cache miss for any caller, 60 times an hour per IP, with no account required, and every generated MP3 was stored in the public blob store forever. A cache hit stays free and open to everyone — so an anonymous reader still hears narration that already exists — but a miss now requires a session, is budgeted per account as well as per IP, and cached audio has a retention policy (older than 180 days is reclaimed, one throttled pass per process per hour, fired from the generation path since the Cloudflare build has no cron handler). Read Aloud is untouched: a signed-out reader falls back to the browser voice exactly as it already did when narration was unconfigured or the quota was spent. Verified with stubbed providers: an anonymous miss returns 401 without ever reaching ElevenLabs, and an anonymous cache hit still returns the audio URL.

- Security: the resource upload's 50 MB cap is enforced by the store instead of the client, and abandoned uploads are reclaimed. The R2 probe handed out a presigned PUT with no length condition, so the limit existed only in the client's JSZip check; the probe now requires the exact byte length, which is signed into the PUT, and oversized declarations are rejected before a URL is issued (the Vercel Blob path already had a server-side `maximumSizeInBytes`). Verified locally against the real signer: the presigned URL's signed headers include `content-length` and a different declared size produces a different signature, so a request that sends any other number of bytes fails the store's signature check. Uploads are also issued under a `resources/pending/` prefix that verification moves them out of, which is what marks an object as claimed; a throttled sweep then deletes only pending-prefix objects older than 24 hours, so the store cannot grow without bound and a resource a submission references can never be caught by it. The round trip was then exercised end to end against a real S3-compatible server (Scality's, in Docker) driving the app's own modules with a test-only endpoint shim: 29 checks pass, including the store refusing a body longer than the signed length (403 `SignatureDoesNotMatch`), a verified ZIP being claimed, a rejected non-ZIP being deleted, missing/forged/cross-object/claimed-prefix tokens all deleting nothing, an unreadable object being rejected with no collateral damage, and the sweep reclaiming stale pending uploads while leaving claimed and non-pending objects alone. That server is not R2, so R2's own behavior and the Workers runtime remain unexercised.

- Security: the guest leaderboard can no longer be farmed by inventing learners. `POST /api/guest-xp` accepted any client-generated id, 120 posts an hour per IP, so one address could mint a board's worth of guests. Identities are now issued by the server: `GET /api/guest-xp` returns an id plus a signed, expiring token (HMAC, keyed by the deployment's auth secret), posting without a valid token for that id is refused, and issuance is limited to 6 new identities an hour per address — which is now the abuse ceiling, since a fake learner needs a token before it can post. Per-identity budgets were added as well. A real device keeps its id and cached token and asks for a new one about once a day, so single-device guests are unaffected. Verified against the real route with a stubbed database: an untokened post returns 401 and writes no leaderboard row, and the identity the route issues verifies; tampered, expired, and cross-identity tokens are all rejected.

- Performance: the notification bell's poll no longer mutates and calls GitHub. `GET /api/notifications` ran retraction deletes (a write across every account under the shared token) and the caller's feedback-resolution sync (GitHub API calls) on every request, so a client polling once a minute multiplied both by sixty for changes that happen a few times a day. Both moved to `src/lib/notification-sweeps.ts`, throttled to once per ten minutes and scheduled from the read instead of awaited by it; each is idempotent, so a missed or overlapping turn is harmless. The response shape is unchanged, and retracted notifications are still never shown — the read filters them out itself, so the guarantee no longer depends on the sweep having run. Verified with stubbed sweeps: the first poll schedules both, polls inside the window add nothing, a poll past the window sweeps again, and fifty further polls add no work.

- Hardening: the JSON-LD sink escapes `<` (`\u003c` inside a JSON string), so a `</script>` in any string can no longer break out of the tag. Only repo-authored static data reaches it today, so this is defense in depth rather than a live fix.

- Reported, not changed: the five dev-only advisories in the `braces` chain have no non-breaking fix; the privacy-policy provider list, the missing CC BY 4.0 avatar attribution, and the absence of any automated test harness all need the maintainer's decision rather than a code guess (the scripted checks above were ad-hoc verification, not a suite). The repo had two affected paths rather than one: `@vercel/blob` pulled `undici@6.28.0`, and `wrangler`'s `miniflare` pins `undici` to an exact version (`7.29.0`), so a plain reinstall would have moved neither. Added scoped `overrides` pinning `undici` to `6.29.0` under `@vercel/blob` and `7.29.1` under `miniflare`; scoped rather than global on purpose, since a single global `undici` override would force `miniflare` back onto `undici` 6.x, which it does not support. `npm audit` now reports zero vulnerabilities, and `tsc`, `eslint`, the Next build (468 prerendered pages), `cf-build`, and a `wrangler dev` route sweep are all unchanged.
