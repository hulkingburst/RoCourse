# Cloudflare deployment

How to serve this site from Cloudflare Workers with `@opennextjs/cloudflare`.

The port is complete and merged on `main`; **Vercel is still the production
host**, and this document is the runbook for the day Cloudflare is actually
deployed. No Worker has been deployed yet — all validation is local
(`wrangler dev` against the real Neon database) plus the Node build — but the
account-side setup is done: Wrangler is authenticated, the
`NEXT_INC_CACHE_KV` namespace exists, and the runtime secrets are uploaded,
so the first deploy is one command.

## Architecture

One codebase, two hosts, no fork:

| Piece | How it works on Cloudflare |
|---|---|
| Worker | `.open-next/worker.js`, built by `opennextjs-cloudflare build`. Serves the Next server, the API routes, and static assets through the `ASSETS` binding. |
| Prerendered routes | Stored in the `NEXT_INC_CACHE_KV` KV namespace as ISR/incremental-cache entries. `populateCache` uploads the build output; `deploy` runs it automatically. |
| ISR | `/resources` and `/showcase` (both locales) declare `revalidate = 60` and write their refreshed entry back to KV at runtime. Revalidation goes through the `memoryQueue` and the `WORKER_SELF_REFERENCE` service binding, which must keep matching the worker name (`rocourse`). |
| Content | The bundle has no `content/lessons` directory, so `src/lib/lessons.ts` probes once and falls back to `src/generated/content-snapshot.json`, regenerated by every build (`npm run content:snapshot`). Node keeps reading the real `.mdx` files. |
| Database | workerd cannot run Prisma — it bans `WebAssembly.instantiate()` — so the Cloudflare build uses the raw Neon serverless SQL layer in `src/lib/db/neon.ts`, exported through `src/lib/prisma.ts`. `PRISMA_ADAPTER` only affects the Vercel/Node path. |
| Uploads | Still Vercel Blob. The R2 presigned path (`FILE_STORAGE=r2` + `R2_*`) is implemented but dormant — R2 needs a payment-verified Cloudflare account. |
| Analytics | `NEXT_PUBLIC_ANALYTICS` is a **build-time** switch: `cloudflare` loads the Cloudflare beacon, swaps the CSP hosts, and sets `images.unoptimized`. Never set it on Vercel. |
| Rate limiting | `trustedIp()` in `src/lib/auth-limiter.ts` prefers `CF-Connecting-IP`, so per-IP limits survive the proxy. |

## One-time setup

1. Authenticate Wrangler: `npx wrangler login`, or export
   `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in the deploy shell.
2. Create the ISR namespace and paste its id into `wrangler.jsonc`:

   ```bash
   npx wrangler kv namespace create NEXT_INC_CACHE_KV
   ```

   `wrangler.jsonc` carries this account's real namespace id (`wrangler kv
   namespace list` reprints it). Local development does not need it —
   `wrangler dev` simulates the namespace under `.wrangler/state` — but a
   deploy reads the real one, so a namespace created in a different account
   must be swapped in before deploying there.

3. Worker secrets (`npx wrangler secret put <NAME>`):

   | Secret | Why |
   |---|---|
   | `DATABASE_URL_UNPOOLED` (falls back to `DATABASE_URL`) | Neon connection string for the HTTPS SQL layer. |
   | `AUTH_SECRET` | Keep identical to Vercel's, or every existing session is invalidated at cutover. |
   | `BLOB_READ_WRITE_TOKEN` | Vercel Blob uploads (the active upload path on either host). |
   | `ELEVENLABS_API_KEY` | Lesson narration (Read Aloud). Optional: without it the button falls back to the browser voice. |
   | `FEEDBACK_GITHUB_TOKEN` | Feedback / showcase / resources filing; those endpoints answer 503 without it. |
   | `FEEDBACK_GITHUB_REPO`, `RESOURCES_GITHUB_REPO` | Optional repo overrides. |

4. Plain vars: `AUTH_TRUST_HOST=true` — committed in `wrangler.jsonc`'s `vars`
   block, so there is nothing to set in the dashboard for it.
5. Defer every `R2_*` variable until R2 exists.

## Build and deploy

```bash
# Local: build, populate the local KV, start wrangler dev
NEXT_PUBLIC_ANALYTICS=cloudflare npm run cf-preview

# Ship
NEXT_PUBLIC_ANALYTICS=cloudflare npm run cf-deploy
```

| Script | Steps |
|---|---|
| `cf-build` | env check → `content:snapshot` → `opennextjs-cloudflare build` → `populateCache local` |
| `cf-ci-build` | env check → `content:snapshot` → `opennextjs-cloudflare build` (what Workers Builds runs; it skips the local cache populate, which only helps local dev) |
| `cf-deploy` | `cf-build` → `opennextjs-cloudflare deploy` (which populates the **remote** KV and then runs `wrangler deploy`) |
| `cf-preview` | `cf-build` → `opennextjs-cloudflare preview` |

Notes:

- `NEXT_PUBLIC_ANALYTICS=cloudflare` must be in the shell of the **build**, not
  just the runtime: it is baked in. It is also more than analytics — it selects
  the Neon SQL database layer in `src/lib/prisma.ts` (Prisma cannot run on
  workerd), so a build without it produces a Worker whose database-backed
  routes fail. The `cf-*` scripts check for it up front
  (`scripts/check-cf-env.mjs`) and stop with a reminder.
- `.dev.vars` (gitignored) is what `wrangler dev` reads locally; deployed values
  come from `wrangler secret put`.
- `wrangler deploy --dry-run` is not a safe validation in this repo: Wrangler
  auto-detects OpenNext and hands its arguments to `opennextjs-cloudflare
  deploy`, which populates the **remote** KV before Wrangler's dry-run flag is
  ever reached. To validate `wrangler.jsonc` without spending writes, run
  `npx wrangler types` (then delete the generated `worker-configuration.d.ts`).
- On Windows the build prints three `Failed to copy …node_modules/hast-util-*`
  errors and a "not fully compatible with Windows" warning. They are harmless —
  the build completes and the worker serves correctly — but WSL is the supported
  path if something breaks.

## Git deploys (Workers Builds)

The Worker is connected to the GitHub repo, and pushes to `main` build and
deploy from Cloudflare. The commands live in the dashboard (Settings → Build).
Workers Builds deliberately does not read custom builds from `wrangler.jsonc`,
so the dashboard is the only place these live:

| Setting | Value |
|---|---|
| Build command | `npm run cf-ci-build` |
| Deploy command | `npx wrangler deploy` — leave the default: Wrangler detects OpenNext and delegates to `opennextjs-cloudflare deploy`, which populates the remote KV and then deploys |
| Build variable | `NEXT_PUBLIC_ANALYTICS` = `cloudflare` |

Why each one matters:

- The plain `npm run build` (`next build`) never writes `.open-next/`, so the
  delegated deploy fails with "Could not find compiled Open Next config, did you
  run the build command?" — the first Git-connected build (2026-10-01) failed
  exactly this way. `cf-ci-build` is `cf-build` minus `populateCache local`,
  which is only useful on a developer machine.
- `NEXT_PUBLIC_ANALYTICS=cloudflare` goes under **Build variables and secrets**
  (not the runtime variables). It is required, not cosmetic — see the note in
  "Build and deploy": it selects the Neon SQL database layer as much as the
  analytics beacon.
- The deploy spends ~473 remote KV writes per build, so it needs the real
  namespace id in `wrangler.jsonc`; the placeholder only works locally. The
  auto-generated Workers Builds API token already includes the Workers KV
  Storage (edit) permission that populate needs.
- Runtime secrets (`AUTH_SECRET`, `DATABASE_URL_UNPOOLED`, …) belong under
  Settings → Variables & Secrets, not Build — they are read by the running
  Worker, not by the build.
- Preview builds only run for branches other than `main`, and this repo deploys
  from `main` only. If preview branches are ever enabled, the default preview
  command (`npx wrangler preview`) is not OpenNext-aware; `npx
  opennextjs-cloudflare upload` is the adapter's way to publish a Worker
  version.

## Verify

- Routes: `/`, `/lessons/<slug>`, `/es/lessons/<slug>`, `/review/<slug>`,
  `/resources`, `/showcase`, `/profile`, `/leaderboard`, `/api/leaderboard`
  should all answer 200.
- ISR: start `wrangler dev --var NEXT_PRIVATE_DEBUG_CACHE:1`, request
  `/resources`, then request it again more than 60 seconds later. The log shows
  `[KVIncrementalCache] get /en/resources` followed by `set /en/resources` — and
  a request inside the fresh window serves the written entry **without** another
  write. That exact sequence was verified locally.
- On a deployed worker, `npx wrangler tail` for runtime errors.

## Free-tier accounting

Cloudflare's limits as of September 2026, and what this site spends:

| Resource | Free tier | This site |
|---|---|---|
| Worker requests | 100k/day | one per page or API request |
| KV reads | 100k/day | one per prerendered page request (plus fetch-cache reads) |
| KV writes | 1k/day | ~473 per deploy, plus one per revalidation |
| KV deletes | 1k/day | rare |
| KV storage | 1 GB | a few MB |

The write budget is the one to watch: two deploys in a day already spend ~950 of
the 1,000 writes. When a limit is hit, KV operations fail and the worker logs
the error; pages still render (a failed read is a cache miss, a failed write
leaves the old entry), they just stop caching.

## Known limitations and upgrade path

- **KV is eventually consistent** — up to ~60 seconds for a write to be visible
  in every location. That is why OpenNext's own recommendation for ISR is R2,
  which this account cannot use yet.
- **The memory queue de-dupes per isolate only** (the adapter calls it
  staging-grade). The production option is the Durable Object queue: add a
  `durable_objects` binding named `NEXT_CACHE_DO_QUEUE` with class
  `DOQueueHandler` plus the `v1` migration (`new_sqlite_classes`), and swap
  `memoryQueue` for `do-queue` in `open-next.config.ts`.
- **R2** (recommended ISR store, optionally behind OpenNext's regional cache)
  needs a payment-verified account. When that exists: create the bucket, add the
  `NEXT_INC_CACHE_R2_BUCKET` binding, and switch the import in
  `open-next.config.ts`.
- **On-demand revalidation** (`revalidateTag` / `revalidatePath`) would also
  need a tag cache (D1 or Durable Objects); the app uses neither today.
- **Uploads** keep going to Vercel Blob from either host until R2 is possible.
- **`maxDuration`** exports are ignored by Workers.
- **At cutover**, set `NEXT_PUBLIC_SITE_URL` to the final host so metadata and
  canonicals are right, and keep `AUTH_SECRET` matching Vercel's.
- **Static asset caching**: Workers Static Assets serve `_next/static/*` with
  `max-age=0, must-revalidate`. A `public/_headers` entry
  (`/_next/static/*` → `public,max-age=31536000,immutable`) restores Next's
  immutable caching, but check how Vercel treats that file first — it is served
  from `public/` on both platforms.

## Where things live

## Environment variables

| Variable | Kind | On Cloudflare |
|---|---|---|
| `NEXT_PUBLIC_ANALYTICS` | build-time | `cloudflare` — swaps analytics + CSP, sets `images.unoptimized`, and selects the Neon SQL layer; a required Workers Builds build variable; never set on Vercel |
| `NEXT_PUBLIC_SITE_URL` | build-time | final public origin (metadata base) |
| `NEXT_PUBLIC_COURSE_NAME` | build-time | same as Vercel |
| `DATABASE_URL_UNPOOLED` / `DATABASE_URL` | runtime secret | Neon HTTPS connection string |
| `AUTH_SECRET` | runtime secret | same value as Vercel |
| `AUTH_TRUST_HOST` | runtime var | `true` |
| `FEEDBACK_GITHUB_TOKEN` | runtime secret | GitHub issue filing |
| `ELEVENLABS_API_KEY` | runtime secret | lesson narration; unset falls back to the browser voice |
| `ELEVENLABS_VOICE_ID`, `ELEVENLABS_MODEL_ID` | runtime secret, optional | pin the narration voice/model (default: the account's "Caleb - Trusted Guide"; on a free plan the library entry is refused over the API and narration automatically speaks with the same voice under its legacy id, so no configuration is needed) |
| `FEEDBACK_GITHUB_REPO`, `RESOURCES_GITHUB_REPO` | runtime secret, optional | repo overrides |
| `BLOB_READ_WRITE_TOKEN` | runtime secret | Vercel Blob uploads |
| `FILE_STORAGE`, `R2_*` | runtime | dormant until R2 exists |
| `PRISMA_ADAPTER` | runtime | Vercel/Node only; ignored by the Cloudflare SQL layer |
| `VERCEL_OIDC_TOKEN` | runtime | Vercel only; not needed anywhere in the Worker |

## Not done yet

- No `wrangler deploy` has run yet; the worker has only been exercised under
  `wrangler dev`. Account setup is done (login, the KV namespace, the runtime
  secrets), but two things still stand in front of a deploy: the Workers
  Builds dashboard needs the settings from "Git deploys" (build command and
  build variable), and `FEEDBACK_GITHUB_TOKEN` must be uploaded before the
  feedback / showcase / resources endpoints can file anything.
- DNS / domain cutover is undecided and out of scope until approved.
- R2 remains blocked on payment verification, so uploads stay on Vercel Blob.
- `ELEVENLABS_API_KEY` is not uploaded yet, so narration currently falls back to
  the browser voice on the Worker; the blob cache it writes to uses the same
  `BLOB_READ_WRITE_TOKEN` already deployed. Note that the token in this
  checkout's `.env.local` is stale — the Blob API answers "Invalid token" — so
  local narration serves freshly generated audio without caching until
  `vercel env pull` refreshes it. Neither the store nor the database is
  required for narration: a failed lookup acts as a miss and a failed store
  returns the audio bytes instead of an error.
