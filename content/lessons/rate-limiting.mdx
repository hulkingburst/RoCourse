The client can now *ask* via RemoteEvents — and that means it can also **keep asking forever**. A server that answers every request without a second thought hands out unlimited coins, or melts under a flood of fake clicks. Rate limiting is the bouncer that decides how often anyone gets in.

<Step>

## The flood

Remember the secure coin flow from the RemoteEvents lesson? The server rewards every `CoinClicked` request it receives. Here is that handler with one obvious problem:

```luau
-- ServerScriptService (this handler runs on the server)
local Players = game:GetService("Players")
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local coinEvent = ReplicatedStorage.CoinClicked

coinEvent.OnServerEvent:Connect(function(player)
    -- trust: every single click is rewarded
    local stats = player:WaitForChild("leaderstats")
    stats.Coins.Value += 10
end)
```

A human playing normally clicks maybe ten times a second — slowly enough for the tool to work. Now imagine a player's client running a loop:

```luau
-- on the exploiter's machine
while true do
    coinEvent:FireServer()
end
```

Every frame, the server receives a fresh request and quietly adds 10 coins. In ten seconds an exploiter has mined more than a legitimate player earns in days — and your server did all the work for it. **An unrelenting client is a fact of Roblox, not a surprise attack.**

## Debounce is UX, not security

You may already know the classic *debounce* for buttons — a local flag that stops the same click from registering twice while a swing or a sound is playing:

```luau
-- LocalScript (on the player's computer)
local isBusy = false

button.MouseButton1Click:Connect(function()
    if isBusy then return end
    isBusy = true
    coinEvent:FireServer()
    task.wait(0.5)
    isBusy = false
end)
```

A debounce feels great to play with: double-clicking doesn't launch the same attack two animations at once. But look at *where* that code runs — on the player's computer, inside local memory. It only stops **that player's own hand** from clicking twice. It never runs for the server.

An exploiter doesn't click the button. They call `coinEvent:FireServer()` directly from their own script, entirely outside your LocalScript. `isBusy` might as well be a different person's phone — the flood arrives at the server identically.

<Tip>
Keep the client debounce for *feel* (no double swings, no overlap), but never rely on it for *protection*. Protection has to run where the real data lives: on the server.
</Tip>

## Server-side cooldown — one per window, per player

The first line of defense is a **cooldown**: at most one accepted request per player per window. Track the last accepted time for each player in a table, check it before rewarding, and update it when you do reward.

```luau
-- ServerScriptService
local Players = game:GetService("Players")
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local coinEvent = ReplicatedStorage.CoinClicked

local COIN_COOLDOWN = 0.2 -- seconds between accepted clicks
local lastClick = {} -- UserId -> os.clock() timestamp

coinEvent.OnServerEvent:Connect(function(player)
    local userId = player.UserId
    local now = os.clock()

    -- too soon since the last accepted click? reject silently
    if now - (lastClick[userId] or 0) < COIN_COOLDOWN then
        return
    end
    lastClick[userId] = now

    local stats = player:WaitForChild("leaderstats")
    stats.Coins.Value += 10
end)
```

Three details do the heavy lifting:

1. **Per player, not global.** `lastClick` is keyed by `UserId`, so one fast player can't drain everyone else's allowance.
2. **`or 0` for the first click.** A brand-new player has no entry in the table; `nil` minus a number errors. `(lastClick[userId] or 0)` means "treat the past as far enough ago."
3. **Reject, don't punish.** The flood gets quietly ignored. If you punished instead, malicious players could *force* a punishment onto themselves to spam-warn everyone.

## Clean up when players leave

That `lastClick` table grows by one entry per player who ever plays, and it never shrinks — a slow memory leak. Players come and go, so clear each player's entry when they leave:

```luau
Players.PlayerRemoving:Connect(function(player)
    lastClick[player.UserId] = nil
end)
```

Without this, every raid that brings a hundred new players leaves a hundred entries behind forever. With it, the table only ever holds the players who are in the game right now.

<Warning>
Per-player state in a server script **must** be cleaned up in `PlayerRemoving`. Tables that track per-player times, counts, or flags — and never clear their keys — are a classic slow leak that shows up only after hours of uptime.
</Warning>

</Step>

## Cooldown vs debounce vs rate limit

These three get mixed up constantly, and the difference matters for what you build:

- **Debounce** — client-side, for *feel*. Stops the same player's hand from double-triggering an action. No access to the server.
- **Cooldown** — server-side. *At most one* accepted request per player per window (`0.2s` between clicks).
- **Rate limit** — server-side. *Up to N requests* per player per window (a burst of 5 per second, say), rejecting anything beyond it.

A cooldown fits actions that should be slow — one coin per click, one jump, one swing. A rate limit fits logs and quick-but-capable actions: a chat box, a stats ticker, a player who can fire 10 projectiles a second but not 10,000. Roblox even has built-in protection on some APIs (like `RemoteEvent:FireServer` rate limits and chat throttling) — but your *own* rules are your responsibility.

## The full hardened flow

Put the pieces together and the economy survives a flood:

```luau
-- client reports a click (normal gameplay, debounce for feel only)
coinEvent:FireServer()
```

```luau
-- server decides: cooldown gates every reward
coinEvent.OnServerEvent:Connect(function(player)
    local now = os.clock()
    if now - (lastClick[player.UserId] or 0) < COIN_COOLDOWN then
        return -- too fast: silently ignored
    end
    lastClick[player.UserId] = now
    player.leaderstats.Coins.Value += 10
end)
```

- **Common mistakes**
- **Global timers.** A single "last interaction at time T" for the *whole game* means one player's flood freezes everyone. Per-player keys, always.
- **Trusting client timing.** `os.clock()` measured in a LocalScript tells you about the player's machine, not your server. Measure where you decide.
- **Rejecting loudly.** Flooding the output or kicking players over a fast click *is* the exploit — it turns a minor abuse into a griefing tool. Silent reject beats noisy punishment.
- **One magic constant for everything.** Picking up a coin and opening a shop deserve different windows. Give each action its own readable constant.
