A shop that's glued to the screen is a billboard, not a menu. A menu *appears* when you ask it to and *goes away* when you're done — and it never eats clicks when it's not up. In the last lesson you built the panel. This lesson gives it the behaviors every interface needs: a button that opens it, a button that closes it, the Escape key, and a click-outside backdrop.

<Step>

## Visible is the on/off switch

Every GUI element has a `Visible` property. `false` makes it — and everything inside it — invisible, unclickable, and skipped when rendering. Crucially, it stays **built**: flip `Visible` back to `true` and the menu reappears exactly as it was, with all its labels and buttons intact.

```luau
shopPanel.Visible = false   -- start the game with the menu closed

shopButton.Activated:Connect(function()
    shopPanel.Visible = true   -- open on demand
end)
```

## One button that toggles

A **toggle button** reads the panel's current state and flips it. The same button opens the menu when it's closed and closes it when it's open — no bookkeeping, no separate handlers.

```luau
shopButton.Activated:Connect(function()
    shopPanel.Visible = not shopPanel.Visible
end)
```

`not` flips a boolean: `not true` is `false`, `not false` is `true`. That one word turns "open" and "close" into a single line.

## The close button (X)

A menu also gets a **close button** — the familiar X in the corner. Its job is simple and one-way:

```luau
closeButton.Activated:Connect(function()
    shopPanel.Visible = false
end)
```

Close is *idempotent*: pressing it when the menu is already closed changes nothing. The toggle is not — a stray click while the menu is in a weird state can re-open it. That's why menus use a dedicated close button: it can never disagree with reality.

## Escape closes it too

Some players live on the keyboard — pressing **Escape** should always be able to bail out of a menu. You've seen UserInputService; this is the shape of the handler:

```luau
local uis = game:GetService("UserInputService")
uis.InputBegan:Connect(function(input, gameProcessed)
    if gameProcessed then return end
    if input.KeyCode == Enum.KeyCode.Escape and shopPanel.Visible then
        shopPanel.Visible = false
    end
end)
```

Two guards matter. `gameProcessed` says "the UI already swallowed this input" — like typing in a TextBox — so you skip it. And `input.KeyCode == Enum.KeyCode.Escape` checks *which* key, because InputBegan fires for every key on the keyboard.

## Click outside to close — the backdrop

The friendliest way to close a menu is to click anywhere *outside* it. That needs a **backdrop**: a full-screen, invisible button sitting *behind* the panel. Because GUI elements drawn later sit on top, create the backdrop first, then the panel — that puts the panel in front.

```luau
local backdrop = Instance.new("TextButton")
backdrop.Size = UDim2.new(1, 0, 1, 0)        -- whole screen
backdrop.BackgroundTransparency = 1         -- invisible
backdrop.Text = ""                          -- no label
backdrop.Parent = screenGui                 -- created BEFORE the panel, so it sits behind

backdrop.Activated:Connect(function()
    shopPanel.Visible = false
    backdrop.Visible = false
end)
```

An invisible backdrop that stays **Visible = true** is a silent click-blocker: the menu looks closed, but the button underneath is eating every click on screen. This is one of the most common "why won't my game respond?" bugs in Roblox — and it's fixed by hiding the backdrop together with the panel.

## One function to rule them all

By now the menu has four ways to change state: the toggle, the X, Escape, and the backdrop. If each one sets `Visible` on its own, they can disagree — and the moment two flags get out of sync is the moment the bug appears.

Route every change through **one function** that decides what "open" means:

```luau
local function setMenu(open)
    shopPanel.Visible = open
    backdrop.Visible = open
end

shopButton.Activated:Connect(function() setMenu(not shopPanel.Visible) end)
closeButton.Activated:Connect(function() setMenu(false) end)
backdrop.Activated:Connect(function() setMenu(false) end)

uis.InputBegan:Connect(function(input, gameProcessed)
    if gameProcessed then return end
    if input.KeyCode == Enum.KeyCode.Escape then setMenu(false) end
end)
```

Now there is exactly one place that knows how to open and close the whole menu — the panel and the backdrop can't drift apart, and Escape, the X, and the backdrop all call the same close.

## Common menu mistakes

- **Backdrop left visible.** The menu looks closed but an invisible button is still eating clicks — the panel and backdrop must be hidden together.
- **Rebuilding the panel on every open.** Building the frame, labels, and buttons from scratch each time is slow and throws away state. Build once, hide with `Visible`.
- **Hiding from the server.** `Visible` is a client GUI property — menus are built and toggled in LocalScripts, on the player's own screen.
- **Forgetting the `gameProcessed` guard.** Skipping it means Escape also fires while the player is typing in a TextBox, kicking them out of the menu mid-keystroke.

<Mistake
  title="Build the menu in a LocalScript"
>
Menus are pure client UI. Building or toggling them in a server Script either does nothing or errors — always build into PlayerGui from a LocalScript.
</Mistake>

</Step>

<Step>

## The checklist on your toolbelt

A menu is just a frame that knows how to show and hide:

- Build it once and start it with `Visible = false`.
- A toggle button flips its own state with `not`.
- The X and the Escape key always close — close can't get stuck.
- A backdrop closes on click-outside and hides *with* the panel.
- Route every entry point through one `setMenu(open)` function.

Run these five habits and any panel — shop, settings, pause menu — behaves like a real interface instead of a billboard.
