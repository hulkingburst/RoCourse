Every Roblox API you've used — `Instance.new`, `:Play()`, `:WaitForChild()` — works because something is an *object* with methods. Luau doesn't have a `class` keyword, but it has **metatables** — the mechanism that makes object-oriented patterns work. If you've ever wondered how `humanoid:LoadAnimation()` works behind the scenes, this is it.

<Step>

## What a metatable is

A metatable is a table that changes how *another* table behaves. The most important operation is `__index` — it tells Lua what to do when you look up a key that doesn't exist:

```luau
localDog = {}
setmetatable(Dog, { __index = Dog })
```

When you ask for `Dog.Bark` and it doesn't exist, Lua checks `__index`. If `__index` is a function, it calls it. If it's a table, it looks up the key there. This is how methods get shared across many objects.

## Building a constructor

A "class" in Luau is a table with a constructor function:

```luau
local Coin = {}
Coin.__index = Coin

function Coin.new(value)
    local self = setmetatable({}, Coin)
    self.value = value or 1
    self.collected = false
    return self
end

function Coin:Collect()
    self.collected = true
    return self.value
end
```

- `Coin.new(value)` is the **constructor** — it creates a fresh table, gives it the Coin metatable, and returns it.
- `Coin:Collect()` is a **method** — the colon syntax passes `self` automatically.
- `setmetatable({}, Coin)` is the key line — it wires the new table to look up missing keys in `Coin`.

```luau
local gold = Coin.new(10)
print(gold.value) --> 10
local reward = gold:Collect()
print(reward) --> 10
```

`gold` is a plain table with two values. But `gold:Collect()` works because when `Collect` isn't found on `gold`, Lua checks the metatable's `__index` (which is `Coin`) and finds it there.

## Inheritance — extending a class

One class can inherit from another:

```luau
local Gem = setmetatable({}, { __index = Coin })
Gem.__index = Gem

function Gem.new(value, color)
    local self = setmetatable(Coin.new(value), Gem)
    self.color = color or "blue"
    return self
end

function Gem:Glow()
    return self.color .. " gem is glowing!"
end
```

`Gem` inherits from `Coin` — a Gem has `.value`, `.collected`, `:Collect()`, and its own `:Glow()`. If Gem doesn't define `Collect`, it falls through to Coin via the `__index` chain.

This is exactly how Roblox's class hierarchy works — `Part` inherits from `BasePart` which inherits from `PVInstance` which inherits from `Instance`.

<Note>
Don't over-inherit. Two or three levels deep is usually the sweet spot. Deep inheritance chains are hard to debug.
</Note>

</Step>

## When to use OOP

OOP shines when you need **many similar objects** with shared behavior:

- Coins, gems, enemies — each has state (value, health) and actions (collect, takeDamage).
- UI components — each button shares click handling but has its own label and callback.
- Wave spawners — each wave shares logic but has different enemies and timing.

OOP is overkill for:
- A one-off utility (just use a table of functions).
- Shared config (a plain table with `return` is enough).
- Event handlers (a connected function is simpler).

## Common mistakes

- **Forgetting `setmetatable`.** A constructor that returns a plain table has no methods. `setmetatable({}, ClassName)` is the whole trick.
- **Using dot syntax instead of colon for methods.** `function Coin.Collect(self)` works but is error-prone. `function Coin:Collect()` passes `self` automatically.
- **Deep inheritance chains.** If you need three levels of inheritance, consider composition instead — give objects a `.data` table instead of inheriting from a parent class.
- **Confusing the class table with instances.** `Coin.new()` returns an *instance*. `Coin:Collect()` is a method on the class — calling it on an instance is wrong.
